# 模型权重管理与使用

更新：2026-11-02（Asia/Shanghai）。适用于普通SFT、RTC-SFT及GUI-RL保存点。目标是能清楚回答“加载哪一个模型、用于初始化/续训/只推理、结果写到哪里”，并避免重复保存或误覆盖大权重。

## 先区分模型用途

| 模型类别 | 内容与用途 | 不能混用的地方 |
| --- | --- | --- |
| 普通SFT | 原有任务VLA，`base_weights`指向具体`<step>/params`；用于RTC-SFT初始化 | 不是本工程完整RL策略，不包含匹配的critic/edit |
| RTC-SFT | 经前缀条件训练的VLA；`rtc_weights`指向具体`<step>/params`，用于新RL初始化 | 不能拿RTC-SFT的完整训练状态当作RL agent恢复 |
| 完整RL checkpoint | 同一步`agent/`＋`params/`＋Orbax提交元数据；用于完整策略只推理或RL续训 | 只取`params/`会丢失critic、edit、target和优化器等状态 |
| GUI续训配套状态 | 同step的`review_state_<step>.json`、W&B身份、已收录经验和实验配置 | 仅有模型可做结构核验/推理；没有配套状态不能声称可完整续训 |

SFT的4000是离线梯度更新步数；GUI-RL的419是累计执行动作步数，两者不能比较。**已保存不等于已更新**：现场第419步保存点的`update_count=0`，不是已完成在线RL优化的模型。是否更好必须通过独立评估判断，不把“最新”命名为“最佳”。

## 目录规划

权重集中留在4090，piperx仅保留客户端、现场配置、GUI轨迹；不复制完整模型到机器人电脑。保留已有路径，不因整理而搬迁历史权重或改旧实验身份。

```text
/data/gcj_data/rl/real_time_expo_ft/
├── code/                         # Git源码、配置模板、使用文档
│   ├── configs/local/            # 本机临时实验配置，不提交
│   └── runtime/gui_server/<id>/  # 服务启动记录和配置快照，不是权重仓库
├── runs/<run_name>_sft/checkpoints/<step>/
├── runs/<run_name>_rl/checkpoints/
│   ├── <step>/{agent,params,...} # 训练产生的完整保存点
│   ├── review_state_<step>.json
│   ├── wandb_id.txt
│   ├── reviewed_episodes/        # 模型恢复配套经验；不要单独清理
│   └── collection_batches/      # 未训练完批次隔离，不自动混入恢复
├── models/releases/<版本名>/    # 命名、固定的保留版本，不是新的训练输出
│   ├── model.json               # 来源、固定step、类别、更新计数、资产哈希
│   ├── source_config.yaml       # 原配置快照
│   ├── checkpoints/<step>/      # 同盘硬链接的完整模型
│   ├── assets/<asset_id>/       # 独立复制的归一化资产快照
│   ├── dataset_manifest.json
│   └── inference.yaml           # RL：只读推理配置
│       # RTC-SFT登记生成initialization.yaml，而非完整RL推理配置
├── evaluations/<独立会话>_eval/  # 推理日志和人工复核结果；不保存新权重
├── assets/                      # 现有训练归一化资产
└── data/                        # 现有示教/训练数据
```

原普通SFT仍在`/data/gcj_data/fast/baseline/openpi/trained_model/checkpoints/`，只读引用，不再复制一份。命名保留用途和实际版本，例如`rtc_h30_b32_sft4000_20261102`、`gui_2836ba_env419_20261102`，避免`latest`、`best`等会漂移或未经评估的名称。

## 方法一：GUI使用已有模型

在piperx打开8888，先结束当前活动会话，再选择使用方式。

| 操作 | GUI设置 | 模型和结果行为 |
| --- | --- | --- |
| 继续训练 | 选择“采集并训练 / 继续训练”，选历史实验，训练总步数大于保存step，点击准备 | 恢复原实验最新完整模型、经验、额度与更新计数；继续写原训练目录 |
| 只推理 | 选择“使用已保存模型·只推理不训练”，选已保存模型，填写本轮推理最大动作步数，点击准备所选模型推理 | 启动时固定保存step，只读恢复完整策略；不恢复训练经验、不执行update、不保存新权重；结果另存evaluations |
| 结束只推理 | 完成本条人工复核后点击“结束推理”，或达到本轮预算 | 保存结果记录并退出；来源模型和训练计数不变 |

只推理的动作步数从0重新计，例如来源419步，本轮可只执行200步；不要求大于419。继续训练则要求总预算大于419，例如填写4000，表示继续剩余3581动作步。网页会显示模型来源目录、保存步数和已知更新次数。

两种方式都先加载与预热，再等待人工确认。每条仍执行固定归位→张开夹爪并确认→采集/推理；准备模型不会自动运动。只推理仍允许人工复核成功/失败，但强制关闭训练收录，不让误传的admitted=True进入经验池。急停与正常结束是不同路径。

GUI默认选择原实验的最新完整保存点，服务启动时固定具体step；已有服务不会在运行中热切换权重。想长期固定某个旧版本，使用下面的命名登记方式。

## 方法二：登记并固定一个命名版本

先确认模型已完整保存，并结束对该run的训练写入；登记时不加载GPU或连接机器人。以下是已知419步模型的实际命令：

```bash
cd /data/gcj_data/rl/real_time_expo_ft/code
uv run --locked python -m piperx_expo.server.model_store register \
  --config runtime/gui_server/2836bafbe83e4d4baa4d25cc9ad457a2/experiment.yaml \
  --checkpoint-dir /data/gcj_data/rl/real_time_expo_ft/runs/rotating_square_h30_gui_v1_20261102_182901_2836ba_rl/checkpoints \
  --step 419 --kind rl \
  --store /data/gcj_data/rl/real_time_expo_ft/models/releases \
  --name gui_2836ba_env419_20261102
```

登记只创建同盘硬链接的选定完整checkpoint，并独立复制小型资产、数据manifest与配置。来源run不移动、不改内容；相同名称拒绝覆盖。数据集保持原绝对路径，原SFT/RTC来源也保留，登记包不复制整套示教数据；使用时仍核对数据manifest和资产一致性。后续原run删除旧数字保存点时，登记版本仍保留。跨文件系统硬链接失败会退出并清理本次临时目录，不会悄悄复制几十GiB。

硬链接不是独立备份：两个目录引用同一批文件，**任何一端都不得原地编辑权重分片或修改共享文件权限**。本工程只用Orbax提交新step目录；命名版本的加载使用read_only=True，禁止清理或写入其checkpoint。需要独立备份时再复制到另一磁盘/存储，并核对完整恢复；本次不自动删除或迁移历史模型。

登记后只读检查：

```bash
uv run --locked python -m piperx_expo.server.model_store verify \
  /data/gcj_data/rl/real_time_expo_ft/models/releases/gui_2836ba_env419_20261102
```

这验证目录结构、提交元数据和小型资产哈希；不遍历大权重做全量内容哈希，也不证明完整模型恢复、推理质量或真机成功率。

RTC-SFT可按相同方法登记，`--kind rtc_sft`、固定step4000、使用匹配的h30服务器配置，输出`initialization.yaml`，其`rtc_weights`指向登记版本的`4000/params`。它用于新RL初始化，不能当作完整RL策略只读恢复。

## 方法三：通过服务管理器加载命名RL版本

在4090执行，服务必须空闲、GPU没有其他任务。管理器只准备模型，不开始运动：

```bash
cd /data/gcj_data/rl/real_time_expo_ft/code
uv run --locked python -m piperx_expo.server.gui_service start \
  --mode eval \
  --model-folder /data/gcj_data/rl/real_time_expo_ft/models/releases/gui_2836ba_env419_20261102 \
  --total-steps 200
```

随后在8888展开“高级分步操作”，在已完成现场预检并勾选运动确认后点击“仅连接学习器”；等模型预热完成，再由现场人员确认本条开始。来源固定为登记版本419，不会因原run新增保存点而改变。结束使用GUI的“结束推理”。命名模型的任意路径只由本机CLI接受，不允许网页覆盖服务器路径。

需要不连接机器人地检查完整模型恢复和RTC延迟时，可使用登记的推理配置执行：

```bash
bash scripts/server.sh rl \
  --config /data/gcj_data/rl/real_time_expo_ft/models/releases/gui_2836ba_env419_20261102/inference.yaml \
  --policy-preflight
```

该路径完整恢复指定RL模型，用离线示教观测预热普通/RTC推理，不创建机器人环境、不做梯度更新；仍需独占GPU，日志写独立评估目录。不要加`--resume`，也不要把它与现场服务同时运行。它不能替代真机正负例或成功率验收。

原CLI的`scripts/server.sh eval`保留用于原CLI客户端，不要将GUI专用配置直接接入其旧逐步协议；GUI只推理走这里的新复核驱动，保留运动前预热和人工开始边界。

## 继续训练与保留策略

- 继续训练使用原实验完整保存点及配套经验；命名release是只读使用版本，不直接在release目录续写。需要从旧版本另开训练分支，应另行设计完整经验/优化器分支迁移，不能只改rtc_weights声称完整续训。
- 保存频率：每条采集不保存模型，整轮采集/更新结束后只保存一次；只推理保存0次新模型，正常结束训练保留最终完整点。checkpoint_interval是上游兼容字段，GUI驱动不按它逐条保存。不恢复逐条全模型保存。当前上游保留上限100个checkpoint，工程未擅自改变或删除旧权重；登记的命名版本通过硬链接独立于原run数字目录的保留计数。
- 建议每个任务长期保留普通SFT来源、已验收RTC基线、最近可恢复RL点、独立评估选出的候选版本。实验日志、模型配置和经验依赖一同保留；清理前核对登记与恢复依赖，不自动清理reviewed_episodes或collection_batches。
- 本次只读磁盘检查：/data约15T、可用约13T；正式RTC-SFT checkpoints约18G，GUI旧实验checkpoints约36G。日志显示每次完整模型数组写入约18.4GiB，磁盘实际占用还受压缩/共享影响，不能按逻辑大小推断可删空间。
- 不提交任何权重到Git；提交源码、模板、三个uv.lock和文档。`models/`、`runs/`、`evaluations/`在项目内也应被忽略；正式数据根目录独立于源码。

## 验收边界

结构核验→完整模型只读恢复/离线预热→现场短回合与人工复核→独立成功率评估，分别记录。登记工具不会自动给模型标记“已验收”或“最佳”。本轮实现、软件与部署证据见[本轮记录](历史/设计/2026-11-02_保存模型使用与权重管理.md)。
