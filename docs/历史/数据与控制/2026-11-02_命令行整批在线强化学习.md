# 命令行整批在线强化学习实施与验证

日期：2026-11-02（Asia/Shanghai）。操作入口见[命令行说明](../../命令行在线强化学习.md)，当前状态见[项目交接](../../项目交接.md)。

## 需求与边界

用户要求：开始时不加载训练经验；rollout→人工成功判定→按轨迹数采够后整批传服务端→训练更新→反复采集；训练数据时间戳在前；急停将本条标失败、采集任务继续。用户明确确认“不使用客户端”指不使用浏览器GUI，保留机器人端命令行和4090远程推理，因此观测/动作的实时传输仍必要。

输入沿用已配置的RTC4000权重、归一化资产、米制绝对7维动作、右腕槽位与现场安全配置；输出为有最终标签的HDF5轨迹、服务端整批原始归档、审核经验和每批完整checkpoint。旧GUI与原自动CLI兼容保留，不修改固定上游算法。默认不发起真实运动、不抢占其他服务。

## 根因与实现

1. 旧`review_train.py`启动时读取全部示教，并直接传给`BatchProcessor`填池；`offline_ratio=0`也会把示教插入在线池。数据同时被用于example_action、critic形状和预热，所以仅调整更新循环不能取消启动加载。
2. 初始化改成7维动作零模板和容量1的零值critic模板。完整训练池、示教和历史审核经验由`prepare_training()`在首批训练时才创建/读取，后续复用。显式`--policy-preflight`仍可读取一条离线示教作预热，不属于正常rollout启动。GUI兼容入口同样延迟加载经验，GUI预算/更新规则不变。
3. 新`client/cli.py`复用既有本地控制状态机、硬件安全与录制器，不开HTTP服务，不使用浏览器心跳和GUI远程管理。`scripts/online.sh`使用独立Python3.10环境；4090使用`rotating_square.cli.yaml`。
4. 新`server/cli_loop.py`采集阶段只计算摘要/审核标签，动作与观测不积累为训练图像档案。采满`episodes_per_batch`后才请求整批清单和每条HDF5，以T/T+1、形状、dtype和SHA256核对，再隔离落盘、入池、固定`updates_per_batch`次更新并保存，重复`rounds`轮。
5. 不从网络反序列化pickle。服务端内部审核经验仍用本进程写出的原格式pickle，保持旧checkpoint恢复接口。
6. 新CLI会话、轨迹、原始批次及默认新实验名均时间戳在前；审核协议ID和正常经验目录仍保留UUID。显式`--run-name`用于恢复原CLI实验，`--resume`不会猜测实验名。实验参数与最终run名另存`experiment.json`。

默认10条/批、3批、每批10次更新，CLI取代旧10条冷启动/按30step额度的调度。算法内部优化、UTD与动作定义不变；这些是可调起始值，不代表真机调参结论。单条200步只用于安全上限，累计`max_steps`不截断CLI批次。回放容量单独配置、有界保留历史。

## 急停及失败数据

- `stop`/Ctrl-C先调用既有硬件停止方法，仅设置当前条停止事件，不关闭任务RPC。当前条强制人工失败，即使自动检测曾报成功，也由人工失败覆盖。
- 若有效动作/观测前缀完整，按失败经验入池：终点reward=0、mask=0；无有效动作或存在动作缺失后继观测时，失败档案仍保留，但拒绝入池；两者都计入本批已结束轨迹数。
- 下一条关闭旧设备会话、重新建立本地环境，必须重新输入READY确认归位，禁止自动恢复运动。归位阶段被打断时尚未录制，不虚构轨迹、不计数，仍等待现场确认。
- 相机失败、网络断开、落盘错误等无法保证数据/控制完整性的故障仍安全退出。未满批次退出不自动传输；隔离原始批次不自动进入checkpoint恢复。
